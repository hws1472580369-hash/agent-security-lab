## 关于"熔断惩罚"（重要，引用数据前请先读）

### 机制是什么

`src/security/risk.py` 里的 `get_history_penalty()`：

> **同一身份**在 **5 分钟内被拒绝 ≥ 3 次** → 后续请求的风险分 **+30**

它只统计**同一个 `agent_id`** 的记录，不跨身份。

### 本批哪些记录被抬高了

| 身份 | 受影响的 id 区间 | 风险分变化 |
| --- | --- | --- |
| `agent_002` | **id 40 – 90** | 基础分 10 → 实际记 **40** |
| `admin_001` | **id 94 – 108** | 基础分 0 → 实际记 **30** |

其余记录（id 1–39、91–93）未受熔断影响。

### 它影响的是哪一步

风险分**只用于第 7 步决策**（≥50 拒绝 / ≥30 待审批 / 其余放行）。所以：

| 拒绝发生在哪一步 | 受熔断影响吗 |
| --- | --- |
| 第 3 步 鉴权（`AUTHORIZATION_DENIED`） | ❌ 不影响——根本不看分数 |
| 第 5 步 资源白名单（`RESOURCE_NOT_FOUND`） | ❌ 不影响——判定与分数无关 |
| 第 7 步 决策（按分数放行 / 审批 / 拒绝） | ✅ **会受影响** |

### 对结论有没有影响

**本批（干净组 L1–L3）中，受熔断影响的记录全部是 `RESOURCE_NOT_FOUND`**——
它们在**第 5 步**就被拒了，判定结果与风险分无关。

**所以：结论不受影响。** 但引用 `risk_score` 时必须注明"含 +30 惩罚"，否则会误读成"这些操作本身风险高"。

### 怎么避免（后续实验）

开跑前确认该身份**最近 5 分钟内没有被拒 ≥ 3 次**。最省事的做法：**跑之前等 2–3 分钟**，或每问一句稍作停顿。
