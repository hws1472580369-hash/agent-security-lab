# Agent Security Lab · 项目框架总览

用途：迷路时先看这一份。它只讲"骨架"，不讲细节实现。

---

## 一、这个项目在干什么

**一句话**：在 LLM 和真实工具之间插一道**确定性的关卡**，让"模型想干什么"和"实际能干什么"分开。

因为模型会被骗（提示注入），所以安全不能放在模型里，只能放在它**绕不过去**的地方。

---

## 二、有两条线，共用一个安全引擎

```
FastAPI 线（原有的，正常业务）
   自己写的 agent_loop ──带 api_key──▶ SecurityEngine ──▶ 工具
                                             ▲
                                             │  同一套九步流水线
                                             ▼
MCP 线（新的，第三方 agent）
   Cherry Studio（第三方客户端）──带 Bearer 钥匙──▶ 网关 ──▶ SecurityEngine ──▶ 工具
```

| | FastAPI 线 | MCP 线（当前主线） |
| --- | --- | --- |
| 谁在用 | 自己写的 agent 循环 | 第三方客户端 + 外部模型 |
| 工具从哪来 | 本地代码 `registry.py` | MCP 协议 → 网关 |
| 身份从哪来 | 请求参数里的 `api_key` | HTTP **请求头**里的 `Bearer` |
| 可信吗 | 自己写的，可信 | 不可信 → 所以要多一层门禁 |
| 安全逻辑 | **同一套** | **同一套** |

## 三、东西都在哪（部署地图）

```
【宿主机 Windows】
  D:\code\agent-security-lab        ← 真实项目（源码 + 备忘录）
        │  共享文件夹（只读、临时）
        ▼

  ├─ vmadmin    管理员：sudo，装东西、看日志

                              │        ↓                    │

                              │ 数据：/app/data/security.db │
                              │      （Docker 命名卷）      │
                              └─────────────────────────────┘
```

## 四、一次调用到底发生了什么

```
用户在 Cherry 里说："客户问支持哪些赎回方式，帮我查一下"
        ↓
模型决定：调用 read_file，参数 {"file_name": "public.txt"}
        ↓
Cherry 带上请求头 Bearer key_agent_002，发 HTTP 到 127.0.0.1:8001
        ↓
【门外】TokenVerifier 拿钥匙查数据库 → 认出是 agent_002 → 放行
        ↓
【门内】九步流水线：
   认证（用外部身份） → 限流 → 工具存在 → 鉴权（有 file.read 吗）
   → Schema（参数合法吗） → 资源策略（public.txt 允许读吗）
   → 风险评分（10 分） → 决策（ALLOWED） → 审计（写一条）
        ↓
真正执行：从容器里读出 public.txt
        ↓
原路返回给 Cherry → 模型总结成人话
```

## 五、四条必须记住的原则

1. **两条线共用一套安全引擎** —— 改一处，两条线都受益。
2. **身份只从请求头来** —— LLM 生成的是参数，钥匙由客户端贴上，模型碰不到。
3. **门外 / 门内是两套东西** —— 门外拒绝（HTTP 401）**不留痕**；门内拒绝（DENIED）**有审计**。
4. **客户端侧的一切都不算防线** —— 提示词、工具开关、权限模式都只是"实验条件"；
   真正的防线只有两个：**网关**（服务端策略）和 **隔离**（容器 + 用户权限）。

## 六、九步流水线（门内）

| # | 步骤 | 判断什么 | 失败时的错误码 |
| --- | --- | --- | --- |
| 1 | 认证 | 身份是谁（外部已认证则直接采用） | `AUTHENTICATION_FAILED` |
| 1.5 | 限流 | 请求是否过于频繁 | `RATE_LIMITED` |
| 2 | 工具存在 | 工具是否注册且启用 | `TOOL_NOT_FOUND` |
| 3 | 鉴权 | 该角色的权限清单里有吗 | `AUTHORIZATION_DENIED` |
| 4 | Schema | 参数是否符合定义 | `SCHEMA_VALIDATION_FAILED` |
| 5 | 资源策略 | 该资源 + 该动作是否允许（含条件） | `RESOURCE_ACCESS_DENIED` / `CONDITION_NOT_MET` |
| 6 | 风险评分 | 动作 + 资源等级 + 角色 + 历史行为 | — |
| 7 | 决策 | ≥50 拒绝 / ≥30 待审批 / 其余放行 | `HIGH_RISK` |
| 8 | 执行 | 真正调用工具 | — |
| 9 | 审计 | 写一条记录 | — |

## 七、实验分组

| 组 | 身份（请求头钥匙） | 内置工具 | 测什么 |
| --- | --- | --- | --- |
| **A** | `key_agent_002`（file_agent） | 全关 | 基线：放行 / 待审批 / 资源策略拒绝 |
| **B** | `key_agent_001`（normal_agent） | 全关 | 鉴权层拒绝（连公开文件都读不了） |
| **C** | `key_admin_001`（admin） | 全关 | 条件不满足（权限最高也可能被挡） |
| **D** | `key_agent_002` | **全开** | 真实组：带本地手脚，测会不会绕过网关 |

## 八、四条攻击路径

```
① 经过客户端 → 经过 MCP → 打网关    提问、文件注入、多轮诱导、改提示词
② 绕过客户端 → 直接打网关 HTTP      伪造钥匙、路径穿越、协议层攻击、资源枚举
③ 绕过网关   → 用客户端自带工具      本地读文件、外联带走数据、自我扩权
④ 绕过技术   → 用"人"当通道          说服管理员放权、让用户贴内容
```

## 十、名词对照

| 名词 | 含义 |
| --- | --- |
| **门外** | MCP 框架的认证中间件（验钥匙） |
| **门内** | 我们的 `SecurityEngine` 九步流水线 |
| **干净组** | 客户端只保留 MCP 工具，本地手脚全关 |
| **真实组** | 客户端本地工具全开，模拟真实 IDE Agent |
| **MCP** | 模型与工具之间的标准协议；本项目用 streamable HTTP |
| **TokenVerifier** | 告诉 MCP 框架"怎么验钥匙"的类，内部查数据库 |
| **数据卷** | Docker 命名卷，容器数据存在虚拟机的 `/var/lib/docker/volumes/` 下 |
| **请求头** | HTTP 头部，钥匙放这里（`Authorization: Bearer ...`） |

---

**记住一句**：

> 模型负责"想"，客户端负责"送"，网关负责"判"，容器负责"关"。
> 错了任何一环，防线就没了。
